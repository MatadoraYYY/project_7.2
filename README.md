# Персональные промо-предложения (Dynamic Pricing)

Прототип системы динамических промо-офферов: расчёт ценовой эластичности,
сегментация клиентской базы, генерация и оптимизация персональных офферов,
планирование кампаний и A/B-сравнение с массовым промо.

Проект №7.2 - «Персонализация и рекомендательные системы».

## Возможности

- **Ценовая эластичность.** Оценка чувствительности к цене по истории покупок, диапазон [0.3, 2.0].
- **Сегментация.** Пять детерминированных сегментов: `new_user`, `repeat_buyer`, `vip`, `dormant`, `price_sensitive`.
- **Генерация офферов.** Девять типов офферов, топ-3 с объяснением причины выбора.
- **Подмешивание пулов.** Дополнительные офферы по эластичности (`price_sensitive`, `price_insensitive`) и по LTV (`high_ltv`).
- **Агент оптимизации.** Определяет тип оффера, его размер, канал доставки и время отправки.
- **Кампании.** Планирование по сегменту с расчётом аудитории и замером результативности.
- **A/B-тест.** Сравнение персональных офферов и массового промо по конверсии и марже.

## Архитектура

```
frontend/            Веб-дашборд (HTML, CSS, JavaScript)
        |  HTTP + JSON
app/api/             Роутеры: customers, offers, analytics
        |
app/services/        Бизнес-логика: elasticity, segmentation, offer_engine,
                     optimization_agent, campaign_service, ab_test_service
        |
app/models/          ORM-модели и Pydantic-схемы
        |
app/core/            config, database, logging, security
```

Каждый слой обращается только к нижележащему, поэтому бизнес-логика не зависит
от способа хранения данных и от транспорта.

## Модель эластичности

Эластичность спроса по цене:

```
E = -(dQ / Q) / (dP / P)
```

Реализация сравнивает среднее количество товаров в покупках со скидкой и без неё.
При истории короче трёх покупок либо при отсутствии одной из групп возвращается
нейтральное значение 0.7. Результат ограничивается диапазоном [0.3, 2.0].

## Правила сегментации

| Приоритет | Сегмент | Условие |
|---|---|---|
| 1 | `new_user` | заказов нет |
| 2 | `dormant` | простой 30 дней и более |
| 3 | `vip` | 10+ заказов и LTV от 50 000 рублей |
| 4 | `price_sensitive` | эластичность 1.2 и выше |
| 5 | `repeat_buyer` | остальные случаи |

## Агент оптимизации

Агент детерминированный: одинаковый вход всегда даёт одинаковый выход.
Такой выбор обусловлен тремя причинами — воспроизводимость результатов
A/B-теста, возможность аудита каждой рекомендации маркетинговой командой
и работа без GPU и внешних квот.

Правила агента:

| Условие | Решение | Канал и время |
|---|---|---|
| Эластичность 1.2 и выше | Процентная скидка, глубина растёт с эластичностью | Предпочитаемый канал |
| Эластичность ниже 0.7 | Бонусные баллы вместо скидки | Сохраняет маржу |
| LTV выше 50 000 рублей | Консьерж-сервис и ранний доступ | Email, вечер |
| Сегмент `dormant` | Глубокая скидка до 30% | Email, выходные |
| Сегмент `new_user` | Бесплатная доставка | Утро следующего дня |
| Активная корзина, клиент реагирует на цену | Фиксированная скидка 10% от корзины | Push, немедленно |
| Активная корзина, клиент не реагирует на цену | Бесплатная доставка | Push, немедленно |

Последнее правило защищает маржу: клиенту, который покупает независимо от цены,
скидка не предлагается даже при брошенной корзине.

## Агент на языковой модели (OpenRouter)

Помимо детерминированного агента доступен второй движок, обращающийся
к языковой модели через API OpenRouter. Оба агента реализуют одинаковый
контракт, поэтому взаимозаменяемы.

| Движок | Эндпоинт | Значение поля `engine` |
|---|---|---|
| Детерминированный | `GET /offers/optimization/recommendations` | `rule_based_v1` |
| Языковая модель | `GET /offers/optimization/recommendations/llm` | `openrouter_llm_v1` |
| Аварийный откат | тот же эндпоинт `/llm` | `rule_based_v1_fallback` |

### Настройка

```bash
# 1. Зарегистрируйтесь на https://openrouter.ai и создайте ключ в разделе Keys
# 2. Добавьте ключ в .env
OPENROUTER_API_KEY=sk-or-v1-...
OPENROUTER_MODEL=nvidia/nemotron-3-super-120b-a12b:free

# 3. Запустите альтернативную точку входа
uvicorn app.main_llm:app --reload
```

Исходная точка входа продолжает работать без изменений:
`uvicorn app.main:app --reload`.

### Валидация ответа модели

Модель рассматривается как источник предложений, а не как авторитет.
Каждое поле её ответа проходит проверку:

- `offer_type`, `channel` и `timing` должны соответствовать перечислениям проекта, иначе рекомендация отбрасывается;
- процентная скидка ограничивается тем же порогом 30%, что и у детерминированного агента;
- скидка полностью удаляется для клиентов, защищённых маржинальной политикой, — при низкой эластичности, у сегмента `vip` или при LTV выше порога;
- `expected_conversion` ограничивается диапазоном [0, 1].

Если ключ отсутствует, запрос к API не удался, ответ не разобрался или все
предложения отклонены валидатором, агент возвращает результат
детерминированного движка. Эндпоинт не возвращает ошибку из-за модели.

Тесты не обращаются к сети: применяется подменный транспорт `httpx.MockTransport`
с заранее заданными ответами.

## Безопасность

- Персональные данные не хранятся, используется обезличенный `external_ref`.
- Валидация входных данных через Pydantic: диапазоны, форматы, длины.
- Ограничение частоты запросов — 120 обращений в минуту с одного адреса.
- В продуктивном режиме операции записи требуют заголовок `X-API-Key`.
- Все значения экранируются перед вставкой в DOM.
- Детали внутренних исключений не передаются клиенту.

## Ограничения

Данные синтетические. Показатели конверсии и маржи демонстрируют методику
измерения эффекта персонализации, а не подтверждённый бизнес-результат.
Для внедрения необходим пилотный эксперимент на фактических данных
с контрольной группой, калибровка коэффициентов маржи и переход на PostgreSQL.
